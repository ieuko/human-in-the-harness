# 具体例：社内勉強会の企画書

状態：架空の利用シナリオです。依頼と回答の往復をCLIで試せる入力を同梱しています。モデルによる企画書の生成や、下記のシナリオ全体の自動実行は未実装です。

この例では、人間への経緯の照会とレビューを利用します。これらの役割、手順、受理を完了条件にすることは、このシナリオ側の設定です。共通基盤の固定された規則ではありません。

## 接続機構をCLIで試す

ビルド後、リポジトリのルートから操作します。

```sh
node dist/src/cli.js submit --file examples/proposal/request.json
node dist/src/cli.js respond '表示された依頼ID' --file examples/proposal/response.json
node dist/src/cli.js get '表示された依頼ID'
```

`request.json`と`response.json`は架空のサンプルです。同じキーで再実行すると同じ依頼が返ります。別の試行には新しいキーを指定するか、`--database`で別の保存先を使います。

## モデルに渡す企画の入力

> 前回の反省を踏まえて、初心者向けAI活用勉強会の企画書を作ってください。参加者は20人、会場を使える時間は2時間、予算は3万円です。目的、当日の構成、運営体制、予算、未確定事項をまとめてください。

## 人間だけが最初に持っている背景

前回は講義が長く、参加者が実際に手を動かす時間が不足しました。担当者は今回は演習を多くしたいと考えています。

公開例にはこの背景を掲載しますが、モデルへの初期入力には含めません。モデルが人間に照会した際に、人間が回答します。

## 想定する進行

1. モデルが、前回の反省を具体的に知らないことを踏まえ、人間への照会を作ります。
2. 共通基盤が依頼を保存して依頼IDを返します。このシナリオの呼び出し側は、回答に依存する検討を待機させます。
3. 人間が「前回は講義が長く、演習時間が不足した。今回は演習を多くしたい」と回答します。
4. 共通基盤が回答を保存し、ハーネスへの接続がモデルに結果を渡します。
5. モデルが企画書の第1版を提出します。
6. このシナリオの設定に従い、その版へのレビューを共通基盤へ依頼します。
7. 人間が「演習の準備と片付けに必要な時間も確保してほしい」と修正を求めます。
8. モデルが第2版を提出し、ハーネスが新しいレビューを依頼します。
9. 人間が第2版を受理します。
10. シナリオ側の完了条件に従い、第2版の本文を完成稿として出力します。

## この例で観察すること

| 観察点 | 対応する理論上の役割 |
|---|---|
| 人間の経験が企画に反映される | 記憶 |
| 人間のコメントによって案が修正される | 評価 |
| 受理された版だけが完成稿になる | 制約の適用 |
| 人間待ちで終了し、同じ作業を再開できる | 時間をまたぐ処理の調整 |

人間の回答には、過去の報告と現在の希望が含まれています。この違いを残せることも確認します。

この手順は逐次的な構成の例です。回答に依存しない予算案などの検討を、人間待ちの間に進める構成も同じ共通基盤で表現します。

## 別の結果も記録する

モデルが経緯を尋ねなかった場合、尋ね方が曖昧だった場合、人間が覚えていなかった場合も観察対象です。想定する進行に一致しなかった実行を隠さず、どこで違いが生じたかを記録します。

再起動や二重回答などの実装上の検証は、[設計案](../../docs/design.md)にまとめています。
