# MCPなどの既存機構との関係

確認日：2026年11月7日。MCPの`latest`は確認時点で2026-07-28版に対応しています。以下ではその仕様とTasks拡張を参照します。各クライアントやハーネスの対応は別に確認します。

## 既存仕様で表現できること

| 仕組み | 提供するもの | 今回の利用候補 |
|---|---|---|
| MCP Tools | ツールの公開、入力と出力の形式、呼び出し | 人間への依頼をモデルやハーネスから利用する入口 |
| MCP Elicitation | クライアントを通じたユーザーへの入力要求 | 同じクライアントのユーザーから回答を得る手段 |
| MCP Tasks拡張 | 永続的なタスクID、状態、結果の取得、途中の入力、取り消し | 人間の応答を待つ処理を非同期タスクとして公開する |
| LangGraphのInterruptsなど | 実行状態の保存、外部入力を待つ中断、再開 | 呼び出し側で人間の結果に依存する処理を管理する |

MCPの[Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)と[Elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)は、人間への問い合わせにも利用できます。2026-07-28版では、追加の入力要求を`input_required`の結果として返す仕組みがあります。Elicitationを同期の入力ダイアログだけとして説明しないようにします。

[Tasks拡張](https://tasks.extensions.modelcontextprotocol.io/)には、人間の応答待ちも用途として含まれています。非同期処理そのものを、このプロジェクト固有の発明として扱うことはできません。

## Tasks拡張との対応

[2026-07-28版のTasks仕様](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html)では、`tools/call`にタスクのハンドルを返し、`tasks/get`、`tasks/update`、`tasks/cancel`で操作します。途中の入力が必要な場合は`input_required`と`inputRequests`を使います。

今回の依頼IDとMCPのタスクIDの対応は、接続側で管理します。人間向けの依頼を受け付ける通常ツールと、その実行を表すタスクを組み合わせる構成を検討します。

回答できないという結果や辞退は、人間が返す結果として表現できます。これを通信やサーバーの障害と区別します。例えば、不承認という業務上の回答が得られた場合でも、タスクとしては結果を得て完了したと扱えるため、業務上の意味をプロトコルの状態だけから推測しません。

Tasks拡張はクライアントとサーバー双方の対応が必要です。未対応のクライアントにタスク結果を一方的に返しません。通常ツールによる「依頼の登録」と「状態や結果の取得」を提供する方式も候補です。この場合、登録の完了と人間の作業の完了を分けて説明します。

## 今回実装する部分

既存の通信仕様に対応するだけでは、次の具体的な実装が自動で揃うわけではありません。

- 依頼を保存するストアと、再送・取り消し・締切・後着入力を扱う処理。
- 人間に依頼と文脈を見せ、回答や質問を受け取る入出力。
- 指定した人間へ依頼を届け、依頼一覧を提示する仕組み。
- 依頼と、呼び出し元の実行・チェックポイント・分岐との対応。
- 結果を取得して、モデルの文脈やグラフの状態へ反映する接続。

これらを再利用できる実装としてまとめ、人間をハーネスの構成要素として差し込めるようにすることを目指します。

## 状態の保存とハーネスの再開

タスクのハンドルを保ち、後で結果を取得できることと、呼び出し元のモデルやグラフが正しい位置から再開することは、別の責務です。

MCPサーバー側で人間の結果を保存しても、クライアント側に取得・結果反映・再開の実装が必要です。グラフを使う場合は、そのエンジンのチェックポイントと依頼IDを結び付けます。[LangGraphのInterrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)は、そのような呼び出し側の中断と再開を検討するための既存例です。

また、Tasksの保存期間を示すTTLと、人間に回答を求める締切は別に管理します。人間側の締切や回答受付の規則は、今回の実装で明示します。

## 実装方針の案

共通基盤に依頼と結果の管理を置き、その上にMCPへの接続、piへの接続、人間側のCLIを実装します。MCP対応を示す際は、対応する仕様の版、Tasks・Elicitationの利用範囲、未対応クライアントでの動作を明記します。

独自の分担規則やワークフローは、利用例に置きます。仕組みの利点や独自性は、既存のMCPサーバーや人間参加型の実装と比較して検討します。
